# 元数据以内嵌为准，刮削只异步补缺

入库时读取文件自带的元数据（EPUB 的 OPF、PDF 的 Info、CBZ 的 ComicInfo；TXT 只能从文件名取书名和作者），这就是这本书的元数据记录。缺失的字段交给后台一个限速 goroutine 按元数据源链去补，以下情况才自动套用：

- 出版书：ISBN 精确匹配。
- 网文：在 xiaoshuohub 上书名与作者完全一致。

其余情况保持原样，需要时通过 API 手动发起刮削，并从候选结果里选一个。用户改过的书会被元数据锁定，刮削不再覆盖。网文和出版书的元数据永远不互相合并。

## 原因

外部配额撑不起全量自动刮削（2026-11-23 实测）：

| 元数据源 | 限制 |
|---|---|
| Google Books | 不配 key 时每日配额为 0；配 key 默认约 1000 次/天 |
| Open Library | 1–3 次/秒 |
| xiaoshuohub | 1000 次/滚动 24 小时，只覆盖网文 |
| 豆瓣 | 官方 API 从 2018–19 年起就不可用 |

详见 `research/Metadata.md`。

## 后果

- 豆瓣默认关闭：现存的接口实际是抓取，有验证码和法务风险，需要用户显式开启。
- Google Books 必须配置 key 才会启用。
- 配额用完，刮削任务就停，等配额窗口滚动后再继续，不重试轰炸。
